Rafeeq Analytics — Backend

A single FastAPI service that turns raw call-centre transcripts, customer messages, and order data (all living in Google BigQuery) into classified, analysed, and predicted customer-experience intelligence, using Google Gemini for language tasks and a trained ML model for cancellation risk.

1. System Overview & Tech Stack

The backend is one deployable FastAPI app exposing a REST API on port 8000. It is organised into three functional "pillars" plus a conversational assistant. All persistent data lives in Google BigQuery; the service holds no database of its own.

ConcernTechnology
Web frameworkFastAPI 0.115 + Uvicorn (ASGI)
Data warehouseGoogle BigQuery (google-cloud-bigquery) — project long-ceiling-343505, dataset reports
LLMGoogle Gemini (google-generativeai), model gemini-3.5-flash
ML (cancellation)scikit-learn, XGBoost, LightGBM, Optuna (tuning), SHAP (explanations), imbalanced-learn (non functional)
ValidationPydantic v2 + pydantic-settings
Data wranglingpandas, numpy
PackagingDocker (python:3.12-slim), uvicorn app.main:app
Legacy files: the repository root contains an older single-file implementation (main.py, analytics.py, bigquery_client.py, gemini_client.py). These are superseded by the modular app/ package. The Dockerfile and README both run app.main:app; the root files are not part of the live service and can be ignored when reading the system.

2. Application Architecture

The app follows a clean three-layer convention everywhere:

HTTP request
   │
   ▼
ROUTER  (app/routers/*)      thin handlers — validate input, call a service, return JSON
   │
   ▼
SERVICE (app/services/*)     business logic; async wrapper around a synchronous _xxx_sync()
   │                          that runs in a thread-pool executor (BigQuery/Gemini are blocking)
   ▼
CLIENT  (bq_client / gemini_service)   shared singletons for BigQuery + Gemini
   │
   ▼
BigQuery  /  Gemini API

Startup (lifespan)

app/main.py wires everything together. On startup it bootstraps the BigQuery tables it owns:

async def lifespan(app):
    await ensure_call_table()      # Pillar 01: reports.call_analysis
    await bootstrap_text_tables()  # Pillar 02: messages / classifications / labels
    yield

Routers are registered in app/main.py. Pillar 03 (cancellation) is imported defensively inside a try/except — if the heavy ML libraries are not installed, that feature is simply disabled and the rest of the API still boots.

7. Pillar 01 — Call Intelligence

Turns call-centre transcripts (English / Arabic / mixed) into structured analysis and dashboard aggregates.

7.1 Analysis flow (write path)

POST /analyse  or  /analyse/batch (≤100 transcripts)
   │
   ▼  calls.py::_process(transcript)
1. call_service.analyse_transcript()  ──►  Gemini (JSON prompt)
        returns {intents[], sentiment, sentiment_confidence, entities{order_ids,
        restaurant_names, areas, product_names, qar_amounts}, summary}
2. if entities.order_ids:  bq_calls.enrich_orders(order_ids)
        ──► BigQuery vendor_kpi + vendor_items_kpi  (parametrised IN UNNEST)
3. asyncio.create_task( bq_calls.save_call_analysis(result) )   # fire-and-forget insert
4. clear_cache()   # drop stale analytics so new calls show immediately
   │
   ▼  returns the full analysis (with enriched_orders) to the caller

Concurrency is capped by a semaphore (5). /predict is a lighter variant: it classifies but skips BigQuery enrichment and persistence — suitable for real-time scoring.

The classification prompt (call_service.py)

A fixed instruction block forces English intent/sentiment labels regardless of transcript language, extracts order IDs in any format (incl. Arabic numerals), and demands strict JSON. The response is _normalise()d: intents filtered to a valid set (fallback general_inquiry), sentiment to {positive, neutral, negative}, confidence clamped 0–1.

7.2 Analytics flow (read path)

call_analytics_service.py runs aggregate SQL over call_analysis (joined to vendor_kpi via extracted order IDs for geo/restaurant insight). All results pass through a 5-minute TTL cache.

EndpointReturns
GET /calls?page=&page_size=Paginated call list; each row enriched in Python with derived agent_name, agent_helpfulness, customer_behavior (keyword scoring of transcript turns)
GET /analytics/summary5 queries: overview counts, intent distribution, weekly sentiment trend, top topics by frequency, top topics by negativity
GET /analytics/area-insightsComplaint/sentiment patterns by area (from transcript entities) + zones (from joined orders)
GET /analytics/restaurant-insightsSame, grouped by restaurant; adds ratings from vendor_kpi

8. Pillar 02 — Support Messages / Text Sentiment

Ingests customer text messages (App / WhatsApp / Ticket), classifies them with Gemini, and serves cross-channel analytics.

8.1 Ingest → classify → serve

INGEST   POST /api/v1/messages/upload  (JSON)  or  /upload/csv
         _build_row(): uuid + preprocess() (PII redaction) + timestamps
         ──► bq_text.insert_messages()  ──► reports.messages

8.2 Text analytics (text_analytics.py → text_analytics_service.py → bq_text.py)

Each endpoint accepts an optional start/end (YYYY-MM-DD) window, validated in the router, applied as a date predicate in SQL. The service aggregates raw BQ rows into typed Pydantic responses.

8.3 Accuracy evaluation

/api/v1/sentiment/accuracy joins classifications to human labels and computes overall + per-class sentiment/intent accuracy and a confusion matrix — the model-quality readout.

8.4 Chat-analytics (chat_analytics.py, prefix /api/messages)

A parallel read surface over the same text data plus chat_history, used by the chat-history views: /stats, /list, /triggers, /sentiment-trend, /cross-channel, and /{chat_id} detail.

9. Pillar 03 — Cancellation Prediction

Predicts the probability that a live order will be cancelled, explains why, and surfaces root-cause analytics. It has two prediction engines and degrades gracefully when the ML model has not been trained.

9.1 Feature engineering — the single source of truth

app/utils/feature_engineering.py is shared by both the offline training script and the online predictor, so training and serving can never drift. Key design rule: no leakage — only placement-time fields are used; every post-delivery field is listed in LEAKAGE_FIELDS and excluded.

  • Placement-time features: hour/day/weekend, order value, distances, pre-order/new-customer/pro flags, payment type, device, platform, cuisine, zones.
  • Historical (rolling) features: vendor 30-day cancel rate, zone 30-day cancel rate, customer prior-order count, vendor avg prep time — computed from prior orders only (rolling window, closed="left") in training; looked up point-in-time from BigQuery at serving.
  • A scikit-learn ColumnTransformer (median-impute + scale numerics; impute + one-hot categoricals) is saved inside the pipeline.

9.2 Training (scripts/train_cancellation_model.py — offline)

1. Pull Delivered + Cancelled orders from vendor_kpi
2. feature_engineering.transform(training=True)   # leakage-free rolling features
3. Time-based split (recent 20% = test; 20% of remainder = val)
4. Handle imbalance: XGBoost scale_pos_weight  vs  SMOTE — keep the better
5. Train LogisticRegression (baseline), XGBoost (primary, Optuna-tuned for recall
   with a precision floor of 0.3), LightGBM (comparison)
6. Evaluate on held-out test → write artifacts/
      cancellation_model.joblib, feature_pipeline.joblib,
      model_metrics.json, threshold_analysis.json, threshold_recommendation.json,
      feature_importance.json, pr_curve.json

Triggered offline or via POST /api/cancellation/model/retrain (which launches the script as a detached subprocess and returns immediately).

9.3 Serving (predictor_service.py)

Model + pipeline are loaded lazily from artifacts/. Engine selection (engine query param):

  • model — ML only; raises 503 (ModelUnavailable) if untrained.
  • gemini — LLM estimate from order signals; works with no trained model.
  • auto — uses the model if trained, otherwise Gemini.
predict_one / predict_batch / live_queue / explain_order
   │
   ├─ model path:  _fill_history() (BQ lookup) → pipeline.transform → predict_proba
   │               → SHAP TreeExplainer top factors → (optional) Gemini explanation
   │
   └─ gemini path: _fill_history() → _gemini_score_row() (LLM probability + factors)
   │
   ▼  bq_predictions.save_predictions()   # persist as read-through cache

Read-through cache: live_queue first reads stored predictions for the candidate orders from cancellation_predictions; only uncached orders are scored (Gemini path capped at 20 new scorings/request so a cold cache can't hang the endpoint — the rest fill in across loads).

10. Conversational Assistant (POST /chat)

A Gemini-backed analytics chatbot (chat.py → chat_service.py). On each request it fetches every analytics source in parallel (call summary, area/restaurant insights, message stats, triggers, sentiment trend, cross-channel, vendor KPI) — each wrapped so a failure is non-fatal — and injects them as a JSON context block under a strict system prompt: the model may only cite facts present in the injected data, must answer in GitHub-flavoured Markdown, and must never invent SQL or statistics. Supports image attachments (multimodal).
